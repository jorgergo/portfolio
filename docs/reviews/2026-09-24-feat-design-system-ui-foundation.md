## Summary

This branch builds spec 0003: six `light-dark()` colour tokens with a print layer, self hosted Plex Mono and Plex Sans through the Fonts API, the page shell (skip link, `<main>`, footer), eight components and five icons, a pure contrast module with a test that parses `global.css`, a dev only style guide, and `design.md`. The code is careful and matches the spec closely. I did not take the verify doc on faith: I built into a scratch folder, served it, and measured focus, hover, print, forced colours, reduced motion, contrast preference, and 320px behaviour in Chromium, and I ran the real contrast module against altered CSS. One real problem needs fixing before merge: Tailwind scans your docs and vendored skills, so the production stylesheet already ships the palette colours, fake bold weights, and pixel sizes your rules ban, and initializing the vendored Tailwind docs skill would flood it.

## Major

### 🟠 Tailwind scans your docs and vendored skills into the production stylesheet, `src/styles/global.css:1`
**Problem**: `@import 'tailwindcss';` uses automatic source detection from the project root. That reaches `design.md`, `docs/specs/**`, `.agents/skills/**`, and `.claude/skills/**`: Tailwind reads Markdown and dot folders. The built `BaseLayout.*.css` carries 37 rules that nothing under `src/` uses. Among them are the exact things your rules ban: `.text-stone-500` and `.bg-red-500!` together with the `--color-stone-500` and `--color-red-500` palette variables, `.font-bold` and `.font-semibold` (weights you do not ship, so the browser would fake them), `.text-[13px]`, `.text-fg/80`, `.duration-150`, `.shadow`, and an invalid rule, `.bg-[--brand-color]{background-color:--brand-color}`. Their source text is the ban lists themselves (`design.md:44`, spec 0003 AC-1, `.agents/skills/tailwind-4-docs/references/gotchas.md`).
**Why it matters**: The dead CSS is small today, but it has three effects. First, the stylesheet hash changes whenever you edit a doc, so a docs only commit busts every visitor's cached CSS. Second, "colours only from the six tokens" holds in markup but not in the stylesheet. A stray `text-stone-500` in a component would render styled instead of doing nothing, so only the verify grep would catch it. Third, the `tailwind-4-docs` skill this branch vendors tells agents to stop and initialize its snapshot, which copies the full Tailwind MDX docs (with examples of nearly every utility) into `.agents/skills/tailwind-4-docs/references/docs/`. Once that happens, the production CSS gains every documented utility. That is likely at the first Tailwind question of the CV page build.
**Suggested fix**: Limit detection to `src/`. Change the import to `@import 'tailwindcss' source('../');` (the path is relative to `src/styles/global.css`), rebuild, and confirm the rules above are gone. The style guide's own classes (`scheme-dark`, `scheme-light`, `sm:grid-cols-2`, `size-8`, and about twenty more) would still ship, because the style guide lives under `src/`. Removing them would need a separate stylesheet for the style guide, which is probably not worth it, so record that trade off in `design.md`. You could also add a verify step that greps the built CSS for `--color-` names outside the six roles.

## Minor

### 🟡 The contrast proof reads only the first `@theme {}` and the first `@media print {}` block, `src/lib/contrast.ts:184`
**Problem**: `blockBody` returns only the first block that matches each header. I ran the real parser from a scratch script. If you append a second `@theme { --color-muted: light-dark(...) }` block, or add a second `@media print { :root { --color-muted: ... } }` after the token block, `parseColorTokens` still returns the old values. The test then checks colours the browser no longer uses, because Tailwind merges theme blocks with the last one winning and the cascade lets the later print rule win. If a print block sits above the token block instead, every print role reads as missing, and the test fails with "missing token" instead of naming the real cause.
**Why it matters**: The CV page and PDF specs will add print rules, and `global.css` is the obvious place to put them. The first colour override in a second block turns the AC-2 guarantee into a false pass, which is the one failure a contrast gate must never have. The comment at `global.css:6` asks readers to keep the blocks as they are, but nothing enforces it.
**Suggested fix**: Make ambiguity fail loudly. Either count the `@theme {` and `@media print {` headers and report more than one as a problem (for example, a `problems: readonly string[]` field that the test asserts is empty), or collect colour tokens from every matching block and let the last one win, the way the cascade does. Add both cases to `contrast.test.ts`.

### 🟡 The vendored `tailwind-4-docs` skill is not initialized, and initializing it drops license restricted docs where git can see them, `.agents/skills/tailwind-4-docs/SKILL.md:18`
**Problem**: `references/docs-source.txt` says "Status: Not initialized", and the skill's quick start tells an agent not to answer until the snapshot exists. Spec 0003 names this skill as the implementation skill for `@theme` and variants, so the first agent that loads it will ask you to run `sync_tailwind_docs.py --accept-docs-license`. That script clones `tailwindlabs/tailwindcss.com` and copies its docs into `.agents/skills/tailwind-4-docs/references/docs/`. No `.gitignore` rule covers that path (I checked with `git check-ignore`). `SKILL.md:30` gives the script path as `skills/tailwind-4-docs/scripts/...`, which does not exist from the repo root; the real path starts with `.agents/`. With `--local-repo`, the script runs `git reset --hard` in whatever directory you pass it.
**Why it matters**: The upstream docs are source available, not open source, and the skill itself says to keep the snapshot local. If the repo is public, a routine `git add .` would commit and publish them. Combined with the major finding above, the snapshot would also flood the production CSS. Until it is initialized, the skill blocks work instead of helping.
**Suggested fix**: Add `.agents/skills/tailwind-4-docs/references/docs/` and `.agents/skills/tailwind-4-docs/references/docs-index.tsx` to `.gitignore` now. Fix the Tailwind source scope (major above). Then either initialize the snapshot on purpose, or have `/sync` note in AGENTS.md that the skill runs in fallback mode (gotchas and playbook only) until you choose to.

## Nits

- ⚪ `src/components/Button.astro:11`, AC-7 says `Button` links turn accent warm on hover and focus, but on `focus-visible` the class list changes only the border, not the text. A keyboard user sees a terracotta border around fg text, while `IconLink`, `TextLink`, and the footer link turn their text terracotta. The spec's own API table has the same gap. Pick one behaviour and align the other; adding `focus-visible:text-accent-warm` is a one class fix.
- ⚪ `src/layouts/BaseLayout.astro:49`, `print:min-h-0` sits on the column, which has no minimum height, so it does nothing. The `min-h-dvh` lives on `body` (line 47) and stays in print. I printed all three built pages to PDF in Chromium and each came out as one page, so nothing breaks today, but AC-11 and `design.md` say the column drops its minimum height. Move the reset to `body`, or correct the text.
- ⚪ `src/components/TextLink.astro:18`, `transition-colors` includes `outline-color`, so on keyboard focus the ring starts in the text colour and fades to olive over 150ms. I measured fg on the `TextLink` and muted on the footer link at the moment of focus, then olive once the transition ended. This follows AC-10 to the letter, but you may want the ring to appear olive at once. Giving interactive elements `outline-color: var(--color-accent)` at rest in the base layer means only the outline style changes on focus.
- ⚪ `src/components/IconLink.astro:29`, `href.startsWith('http')` also matches a relative path such as `httpie-notes`. Checking for `https://` or `http://` says what you mean.
- ⚪ `src/lib/contrast.ts:60`, `contrastRatio` and `apcaContrast` accept any `string` but return `NaN` for `#fff`, named colours, or `rgb()`. Only parser output reaches them today, so this is safe. A short comment on the exports, or a branded `Hex` type, would stop a later caller from getting `NaN:1` in the style guide.
- ⚪ `design.md:131`, the file promises that values live only in `global.css`, yet it restates 640px, 24px, 480px, 40px, and line height 1.6. These are derived values, not tokens, so the problem is mild, but they will drift the day a token changes. Point at the utility instead (`max-w-content`, `px-6`, `xs`).
- ⚪ `.claude/launch.json:1`, this file is untracked. Decide whether it is shared tool config (commit it) or local config (ignore it), so it does not slip into a later `git add .`.

## Strengths

- The contrast maths is right. `apcaContrast` matches the APCA 0.0.98G constants and clamps, and the WCAG path uses the current 0.04045 threshold. Running the real module reproduced every number in the spec (for example, light muted 4.642:1 at Lc 66.56 and dark hover 7.592:1 at Lc 55.44, negative polarity). The break value `#8d8576` gives 3.13:1 and Lc 53.7, so AC-2's regression claim holds.
- The style guide really is dev only. It combines the `_dev` folder, which Astro never routes, with an `injectRoute` that runs only when `command === 'dev'`. My production build contained `404.html`, `cv.html`, `index.html`, one stylesheet, four fonts, the favicon, and `_headers`, and nothing named styleguide.
- Fonts meet AC-3 exactly: four woff2 files, one preload (Plex Mono 400), every request same origin, a CSP meta with `font-src 'self'` and hashes for both font styles, and no console violations on the three built pages. Only weights 400 and 500 load.
- Behaviour I measured in Chromium matches the spec. The skip link is the first tab stop. Enter moves focus to `<main>` with no ring. Then comes the `TextLink`, then the footer link, with a 2px solid olive ring offset 3px (`rgb(186, 170, 124)` in dark). A mouse press gives no ring. Hover turns text and underline terracotta. `prefers-contrast: more` gives a 2px underline and an fg footer. Forced colours keep the underline on the footer link. Reduced motion drops transitions to 0.01ms. Print gives a white ground, an 11pt root, no column padding, and hides the skip link and home link. At 320px nothing scrolls sideways.
- Small decisions are well reasoned and recorded where the next reader will look: `Astro.routePattern` instead of the pathname (with the `build.format: 'file'` reason), `theme-color` metas computed from the parsed tokens, scheme suffixed ids so the two style guide panels do not duplicate `id`s, and the tight `TextLink` markup that avoids an underlined stray space.
- The gate is green: `pnpm test` (134 tests), `pnpm lint`, `pnpm format:check`, and `astro check` (0 errors) all pass. The `style=""`, `define:vars`, `is:inline`, `set:html`, `dark:`, hex, and `target=` greps over `src/` all come back empty. No commit carries a Claude co author trailer.

## Test coverage

`src/lib/contrast.ts` is well covered. The tests include WCAG and APCA reference fixtures in both polarities, the equal colours case, and the parser on a sample with a comment, a non hex value, Prettier style wrapping, a nested `@page`, and a missing block. They also check every `CONTRAST_PAIRS` entry in all three schemes, with failure messages that name the pair, the scheme, both colours, and the floor. The gap is the parser case in the minor finding above: no test covers a second `@theme` or print block. The component and layout logic has no automated check: the `routePattern` home link branch, the computed `theme-color` metas, the single font preload, and the absent style guide in `dist/`. That is deliberate until Playwright arrives with `/test`, and the verify doc covers these by hand. When `/test` runs, the cheapest wins are a post build test over `dist/` for the metas, the preload count, the four fonts, the absent style guide, and the colour variable names in the built CSS. None of those needs a browser.
