## Minor

### 🟡 The employer guard is case sensitive, unescaped, and misses `Liverpool`, `e2e/site.spec.ts:1557`
**Problem**: The test builds `new RegExp(`\\b${employer}\\b`)` from each `cv.work[].name` and from its first word when that word is longer than three letters. With today's content that yields `Ford Motor Company`, `Ford`, `El Puerto de Liverpool`, `Daimler Truck Mexico`, and `Daimler`. So `Liverpool` on its own is not caught (the first word `El` is skipped), `ford` in lower case is not caught, and a future employer name holding a regex character (`Inc.`, `A+B`, a parenthesis) gives a wrong pattern or throws before it ever runs. The manual `grep -c -i 'ford\|liverpool\|daimler'` step in `verify.md` is case insensitive and names all three, so the automated test is weaker than the check it stands in for.
**Why it matters**: This is the only automated guard for the spec's first key invariant (no employer on `/about`), and it exists so a later content edit is caught by CI rather than by eye. Today's content passes and nothing wrong ships, which is why this is a Minor.
**Suggested fix**: Escape each name before it goes into the pattern, add the `i` flag, and widen the words you derive: for example every word of four or more letters from each name, so `Liverpool`, `Motor`, `Truck`, and `Mexico` join the list. If a plain word such as `Mexico` might legitimately appear in a future line, keep a small skip list beside the test and say why. Either way, note in the test comment which words it checks, so the next content edit knows what it will trip.

### 🟡 Two manual Safari steps are unticked while the Known gaps line says they were done, `docs/specs/0009-about-page/verify.md:9`
**Problem**: The uncommitted `verify.md` edit ticks every step except two: the Safari and Chrome zoom on a marker (line 9) and the VoiceOver read (line 12). Its Known gaps section (line 46) says "the Safari look is checked by eye above", which is not yet true, and spec 0009's status is still `In Progress`. The CDP font check in `e2e/site.spec.ts` proves the `›` draws in Plex Mono in Chromium only.
**Why it matters**: The marker glyph in a system fallback face is exactly the defect the spec set out to avoid (it is why `›` was chosen over `←`), and Safari is where the footer arrow already falls back. The risk is low, since the same `latin` file serves every browser, but the record says the check happened and it has not.
**Suggested fix**: Run the two steps before opening the PR and tick them, or leave them unticked and change the Known gaps sentence to say they are still owed. Then set the spec's status to match.

## Nits
- ⚪ `src/pages/about.astro:28`, the marker span ships as `<span …>\n›\n</span>` (see `dist/about.html`), not AC-6's `<span …>›</span>`. It is harmless: the span is `aria-hidden`, and as a flex item its leading and trailing whitespace collapses, so the glyph sits at the column edge and every test passes. Either write it tight under `prettier-ignore` as the closing is, or soften the markup sentence in AC-6.
- ⚪ `src/pages/about.astro:35`, the page uses the "comment on its own line before the tag" form that `TextLink` and `SkipLink` just moved away from because it leaves a newline that prints as a space. It is safe here because the parent is a flex column, where whitespace between items never renders; say so in the comment, or use the same wrapped expression, so the next reader does not wonder which form is right.
- ⚪ `src/lib/site-meta.ts:90`, `givenName` splits on `\s+`, which includes the no break spaces that `nameParts` in `src/lib/cv-schema.ts:102` deliberately keeps together for the card. A name written `Ana María Ruiz` gives `Ana` in the description and `Ana María` on one card line. Record it in the spec's Consequences or reuse the same boundary.
