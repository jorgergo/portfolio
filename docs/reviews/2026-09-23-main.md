## Major
### 🟠 Third party screenshots would be committed to a public MIT repo, `referece-images/`
**Problem**: The folder holds eight PNG screenshots (7.1 MB total) of fbold.dev, t3.gg, and cv.jarocki.me. It is not ignored, so the first commit will carry it. The spec's project layout does not include it, the folder name is misspelled, and the README's "all rights reserved" carve out only covers your own CV content, so these files would sit under the MIT license header by default.
**Why it matters**: Screenshots of someone else's site are their copyrighted work, and this repo is meant to be public and part of your portfolio. Binary files also stay in git history even after you delete them later, so the only cheap moment to keep them out is now, before the first commit. 7 MB of images also slows every clone and every Cloudflare build checkout for no runtime benefit.
**Suggested fix**: Keep them out of the repo. Either add `referece-images/` to `.gitignore` (or rename it to `reference-images/` and ignore that), or move them somewhere outside the project. The scope already links to the live sites, which is enough for the design spec to point at. If you do want references in the repo later, use your own sketches or wireframes, not captures of other people's pages.

## Minor
### 🟡 `minimumReleaseAgeExclude` overrides pnpm's cooling off period for a release that was hours old, `pnpm-workspace.yaml:4`
**Problem**: wrangler 4.137.0 was published on 2026-09-23 at 14:03 UTC, a few hours before the scaffold. pnpm 12 refused it under its default minimum release age, and the scaffold worked around that with `minimumReleaseAgeExclude: wrangler@4.137.0`. The spec never planned this line, and it becomes dead config once the release is a day old.
**Why it matters**: The release age rule is a supply chain guard, so an exclusion should be a conscious choice with a reason next to it. Left as is, it is a puzzle for whoever reads the file next week, and it suggests a habit of excluding whatever pnpm blocks.
**Suggested fix**: Either remove the line after 2026-09-24 (the lockfile already pins 4.137.0, so installs keep working), or keep it and add a one line comment in the spec's version pins section explaining why it was needed and when it can go. Do not carry it into `AGENTS.md` as a convention.

### 🟡 Spec still says build approvals live in `package.json`, `docs/specs/0001-stack-architecture/index.md:44` and `:119`
**Problem**: The spec's stack table and config section say `pnpm.onlyBuiltDependencies: ["esbuild", "workerd"]` goes in `package.json`. pnpm 12 reads approvals from `pnpm-workspace.yaml` under `allowBuilds`, and that is what the scaffold correctly did. The spec's escape clause at line 180 said to "note it in `AGENTS.md`", but `AGENTS.md` does not exist until feature 2 runs `/audit`, so right now nothing records the change and the spec contradicts the code.
**Why it matters**: The spec is the only project context agents read today. The next agent that follows the spec literally will add a `pnpm` block to `package.json` that pnpm 12 ignores, and then wonder why the "ignored build scripts" warning is back.
**Suggested fix**: Make the small in place edit to the spec now (lines 44 and 119, and the line 180 bullet) so it says `allowBuilds` in `pnpm-workspace.yaml`, then let `/audit` copy the convention into `AGENTS.md` when it creates the file.

### 🟡 Node 26 is only active when you remember to `fnm use`, `.nvmrc:1` and `package.json:7`
**Problem**: A fresh shell on this machine runs Node 22.14.0 (`node -v` in this review). `.nvmrc` says `26` and `engines.node` is `>=26`, but `engine-strict` is off by spec, so pnpm only warns. `verify.md` ticks `node -v → v26.x`, which is true only inside a shell that ran `fnm use`.
**Why it matters**: Anyone, including agents, who runs `pnpm build` from a fresh shell builds and checks on Node 22, a different major than the one the spec picked and the one Cloudflare will use. The gap will surface as "works locally, breaks in CI" (or the other way round) at exactly the time you least expect it.
**Suggested fix**: Run `fnm default 26` once on this machine, or enable `fnm env --use-on-cd` in your shell so `.nvmrc` is honoured automatically, and add a line to the README saying so. No change to the repo files is needed for the spec's decision itself.

### 🟡 Shiki warning fires on every dev and build, `astro.config.mjs:9`
**Problem**: Astro warns "Shiki syntax highlighting uses inline styles that are not compatible with Content Security Policy" because `security.csp` is on and `markdown.syntaxHighlight` still defaults to shiki. Nothing renders markdown today, so it is noise for now.
**Why it matters**: The warning will drown out real ones, and the moment the content model adds markdown with a code fence, the hashed `style-src` will block the highlighter's inline styles and code blocks render unstyled. The spec's CSP rules ("classes only") already forbid the escape hatch, so this needs a decision, not a config tweak on the fly.
**Suggested fix**: Add a follow up bullet to spec 0001 for the Content model spec: pick `markdown.syntaxHighlight: false` (no code blocks on a CV site) or `'prism'` with a stylesheet. Leave `astro.config.mjs` as the spec wrote it until that spec lands.
